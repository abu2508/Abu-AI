## 3. Generated TypeScript findings
1. **Optionality is less precise than the wire (M82-G7).** `ToolResults` keys and `AnalyseTool` optional fields are emitted as required `X | null` because openapi-typescript treats defaulted properties as required, but the server **omits** tools that did not run and omits the median keys when timestamps are unreliable. The generator flag `--default-non-nullable false` fixes these but changes **21 schemas** including `OrchestratorResponse`, `Usage` and `ContextInfo` fields that the server always emits, so it is **not** adopted. Decision: runtime validation is zod (absent or null accepted); compile-time guards compare zod output to the generated types and document the intentional differences.
2. Tuples render correctly (`expense_by_category: [string, string][]`); `InsightOut.params` is `{[key: string]: string | number | null}`; `HabitsTool.habits` is `(HabitDays | HabitWeeks)[]` (narrowable on the literal `unit`); money, dates and ids are plain `string` (patterns are not carried into TypeScript), so the zod layer keeps the numeric-string and ISO checks.
3. `ToolResults` members are unions `Result | ToolError` without a discriminator (M82-G9): narrow with `"error" in value`.
4. Existing consumers unchanged: only `OrchestratorResponse` changed among existing schemas (B3 report). `api:types:check`, `tsc` and `check:all` pass at B3.
5. Error envelopes: `DetailEnvelope`, `ErrorEnvelope`, `RunFailedEnvelope` are generated; `ErrorBody.code` is an open `string` whose description lists the known orchestrator and domain codes.

## 5. Redirect / credential-leak spike, revisited (security blocker stays)
Method: source reading of the installed `expo@57.0.34` and `react-native@0.86.3`. No device, simulator or network test was possible here, so **nothing below is device-verified**.
| Finding | Evidence |
|---|---|
| `globalThis.fetch` is `expo/fetch` by default on native; RN's XHR fetch is used only if `EXPO_PUBLIC_USE_RN_FETCH` is `1`/`true` | `node_modules/expo/src/winter/runtime.native.ts` lines 38-53 |
| `expo/fetch` forwards `redirect` to native (`follow` default) | `src/winter/fetch/fetch.ts` (`redirect: redirect ?? 'follow'`) |
| iOS: for `manual` and `error` the redirect is not followed (`completionHandler(nil)`), the 3xx is delivered; `error` raises `FetchRedirectException`; cookies off unless `credentials: include` | `ios/Fetch/NativeResponse.swift` ~190-205, `ExpoURLSessionTask.swift` ~25-35 |
| Android: `followRedirects(false)` unless `follow` | `android/.../fetch/NativeRequest.kt` 44-45 |
| RN's own fetch has no redirect control | no `redirect` handling in `react-native/Libraries/Network` |
| M8.1 passes `redirect: "manual"` and `credentials: "omit"` but via the implicit global | `mobile/src/auth/runtime.ts`, `src/api/http.ts` |
Assessment: **probably safe by default, not demonstrated, and fragile**: an environment flag or a dependency that bypasses the winter runtime silently restores redirect-following. The leak is wider than the `Authorization` header: 307/308 would resend the **enrollment code and the refresh token** in the body. Therefore authenticated live connectivity on **native** remains blocked. Plan revision 2 (section 9.2) adds: an explicit un-switchable `expo/fetch` transport module with lint and CI gates, a fail-closed native credential gate (`NATIVE_AUTH_TRANSPORT_VERIFIED = false`, visible in About), a transport-only redirect canary with fake credentials, a real-HTTP Jest redirect test (labelled as not proving iOS), and a rule that the gate flips only in a reviewed commit citing device evidence. Web (Playwright) is spec-safe (opaque redirect) and is not gated. This tightens M8.1 on native; it needs your approval (decision D5').
