## 1. Scope and non-goals
**Goal.** Give the mobile app precise, machine-checkable response contracts for exactly what M8.2 reads, so `openapi-typescript` generates real types and contract drift is caught mechanically.
**In scope**
1. `GET /v1/finance/summary`, `/v1/finance/insights`, `/v1/finance/upcoming`.
2. `GET /v1/coach/briefing`.
3. The result shape of **all 18 orchestrator tools** (every tool the M8.2 cards may render inside `OrchestratorResponse.data`): `finance.{summary,cashflow,budget_status,insights,upcoming,loans,cards,subscriptions,pending_count}`, `messaging.{analyse,reply_suggestions,summary}`, `coach.{plan,briefing,review,progress,habits,goals}`.
4. The error contracts: orchestrator/domain envelope `{"error":{"code","message"}}` (plus the run-failure variant with ids) and the `{"detail":...}` envelope (auth, middleware, infrastructure).
5. Tests proving the models match real synthetic outputs and that behaviour is unchanged; regenerated OpenAPI snapshot and mobile types.
**Non-goals (hard constraints).** No migrations, no endpoint added/removed/renamed, no query-parameter change, no business-logic change, no auth/authorization change, no new dependency, no status-code or error-code change, no field added/removed/renamed/re-typed in any response, no external model call, no production data, no real message or financial content in fixtures. Latent defects found during the investigation are **reported, not fixed** (section 9).

## 3. Exact current response shapes (from source; every field is reproduced as-is)
Serialisation facts that govern the models. **Domain routes** return `jsonable(...)` (`domain/common/jsonable.py`): `Decimal` -> exact string (never float), `UUID` -> str, `date`/`datetime` -> `.isoformat()`, tuples/sets -> lists. **Orchestrator tool results** are raw Python objects placed in `data: dict[str, Any]` and serialised by Pydantic's JSON mode; `Decimal` -> string, `date` -> ISO. `finance.summary` etc. therefore have the **same logical shape** on both paths. Money is always a string quantised to 2 places by `analytics.q` except where noted. "?" = may be absent, "null" = may be null.

### 3.1 R1 `finance/summary` and T1 `finance.summary`
`{start: date, end: date, income: money, expense: money, net: money, savings_rate_pct: money|null (null when income == 0), expense_by_category: [[category:str, amount:money], ...] (list of 2-element arrays, sorted by amount desc then name; zero categories omitted; refunds may make an amount negative), income_by_category: [[str, money], ...], pending_review_count: int}`. `pending_review_count` is **not** included in the figures above (comment at `service.py:742`).

### 3.2 R2 `finance/insights` and T4 `finance.insights`
R2 returns a JSON **array**; T4 returns `{"insights": [...]}`. Item: `{code: str, severity: "info"|"warning"|"alert", params: object, text: str}`. `text` is a fixed template filled from `params` (`analytics.py:360-372`), so it is safe to display verbatim. **`params` varies by `code`** (ambiguous, see section 9): `top_category {category,amount,share_pct}`; `spending_exceeds_income {deficit}`; `low_savings_rate {savings_rate_pct}`; `category_increase {category,previous,current,change_pct}`; `budget_exceeded {category,limit,spent}`; `budget_near_limit {category,pct}`; `unusually_large_expense {date,amount,typical}`; `upcoming_due` = an upcoming item (`{kind,label,amount,due}`). Sorted by severity (alert, warning, info) then code.

### 3.3 R3 `finance/upcoming` and T5 `finance.upcoming`
R3: array; T5: `{"upcoming": [...]}`. Item: `{kind: "subscription"|"emi", label: str, amount: money, due: date}`; `label` is decrypted user text. `amount` for an EMI is the stored `emi_amount` and for a subscription the stored `amount` (stored scale, not re-quantised here: formatting inconsistency noted in section 9). Sorted by `(due, kind)`.

## 4. Proposed Pydantic models and nesting
Location: a new package `services/api/contracts/` (pure data models; **imported only by OpenAPI/doc wiring and tests, never by request handling**), so removing it cannot alter runtime behaviour.
```
contracts/
  common.py     Money = Annotated[str, StringConstraints(pattern=r"^-?\d+(\.\d+)?$")]; IsoDate; IsoDateTime; _Base(extra="forbid")
  errors.py     ErrorBody{code:str, message:str}; ErrorEnvelope{error}; RunFailedEnvelope(ErrorEnvelope){run_id, execution_id|None, trace_id|None}; DetailEnvelope{detail:str}
  finance.py    SummaryOut; InsightOut (+ InsightParams); UpcomingItem; CashflowOut; BudgetRow; LoanRow; CardRow; SubscriptionActive/Suggested; per-tool wrappers (InsightsToolOut, UpcomingToolOut, BudgetsToolOut, LoansToolOut, CardsToolOut, SubscriptionsToolOut, PendingToolOut)
  coach.py      EventOut; BlockOut; UnscheduledOut; ReminderOut; MoodTrend; PlanOut; BriefingOut; ReviewOut; ProgressOut; HabitDays | HabitWeeks (discriminated by `unit`); GoalView; HabitsToolOut; GoalsToolOut
  messaging.py  AnalyseOut (all analysis keys optional except message_count/platform/conversation_id/instruction_like_messages); DraftOut; SuggestionsOut; SummaryToolOut
  tools.py      ToolError{error:str}; ToolResults{ "finance.summary"?: SummaryOut | ToolError, ... all 18 keys optional }
```
Design rules: (1) every model `extra="forbid"` (an unexpected field fails the conformance tests, which is the drift alarm; this surfaces as `additionalProperties:false` in OpenAPI and is harmless to clients); (2) money is typed `str` with the numeric-string pattern, never `Decimal`/`float` (documentation matches the wire); (3) dates/datetimes are `str` with `format` hints (the wire is a string, and UTC offset spelling differs between paths, section 9); (4) nullable fields are `X | None` **and required** where the producer always emits the key, optional (`= None` default, `exclude`-safe) only where the producer omits it (analysis timestamps-dependent keys, habit weekly/daily keys); (5) enums only where the producer's set is closed in source (`severity`, budget `status`, card `band`, `kind`, `last_sender`, plan `reason`); open `str` elsewhere (`code`, loan/goal `status`, `source`); (6) `expense_by_category`/`income_by_category` stay `list[tuple[str, Money]]` (do not reshape the wire).

## 5. Error-contract strategy
Document, never emit. Per route group add `responses={...}` entries (documentation only) mapping status -> `ErrorEnvelope`, `RunFailedEnvelope`, `DetailEnvelope` using the inventory in 3.9. `code` stays `str` with the known set listed in the description (a closed enum would make a future backend code break strict client parsing). A conformance test enumerates every `error.code` the backend can emit (scan of `OrchestratorError(`/`*Error(` call sites plus the `_classify_error` table) and asserts each is in the documented list, so adding a code without updating the contract fails. Statuses are asserted per code in a table test that drives real requests (kill switch on, spending exhausted, wrong key reuse, malformed body, no token, rate-limit burst). 401/422/429/503 are attached to every authenticated route in the covered set; routes outside B3 are not modified.

## 6. How validation is added without changing runtime behaviour
- **Mechanism: documentation-only, not `response_model`.** For each covered route add `responses={200: {"model": SummaryOut, ...}, 401: {...}, ...}` to the decorator and **leave `-> Any` and every `return` untouched**. FastAPI then publishes the schema but performs no validation, filtering, coercion or re-serialisation on the response (so no Decimal/datetime/tuple behaviour can change). A guard test asserts `route.response_model is None` for every covered route so nobody later converts it to enforced validation by accident.
- **Orchestrator `data`.** Changing the `data` annotation would touch serialisation of the existing model, so B3 leaves `OrchestratorResponse` as is and publishes `ToolResults` by post-processing the generated OpenAPI document in the one existing generation path (`services/api/openapi_export.py` / `openapi_dev.py`): register `ToolResults` and its members in `components.schemas` and add a `$ref`-based description on `OrchestratorResponse.properties.data` (`additionalProperties`/`properties` referencing `ToolResults`). Runtime responses are byte-identical. (Alternative needing your decision, D2: annotate the field with `json_schema_extra` in `core/orchestrator/types.py`; no runtime effect either, but it edits a core module.)
- **Validation of real outputs** lives in tests only (section 8): the models are applied with `model_validate` to bodies captured from the live synthetic app.

## 8. Test strategy and acceptance criteria
**Fixtures.** Synthetic only: invented names ("Demo Supermarket (demo)"), round amounts, fixed clock, no real contacts or message bodies (conversation fixtures use content-free templated phrases already used by the existing suite). Stored under `tests/contracts/fixtures/` as JSON; a scan test fails on emails, phone-like numbers, card-like digit runs, or URLs.
**Test layers**
1. `tests/unit/test_contract_models.py` (no DB): each model validates its golden fixture; rejects missing required field, wrong type, float money, unknown extra field; accepts nullable and optional variants explicitly: `savings_rate_pct: null`, `projected_month_expense: null`, `limit: null`, `band: null`, empty lists everywhere (no insights, no upcoming, no blocks, no habits), `AnalyseOut` empty-conversation variant, timestamps-unreliable variant (no median keys), `HabitDays` vs `HabitWeeks` discrimination, `{"error": ...}` tool results, truncated results, UTC `Z` vs `+00:00`.
2. `tests/integration/test_contract_conformance.py` (needs the existing Postgres test harness): create synthetic users/data through the **existing API/services** (accounts, transactions, budgets, loans, subscriptions, cards; tasks, events, habits, goals, reminders, check-ins; shared and unshared conversations), call R1-R4 and drive every orchestrator workflow, then `model_validate` the real response bodies against the models, including every `data[<tool>]`. Cover the empty-user case and each nullable branch (no income, unreliable timestamps, weekly vs daily habits, goal without a deadline, card without limit).
3. Error conformance: drive each documented failure for real (401 no/garbled token, 422 bad input, 403 not_shared, 409 idempotency conflict and in-progress, kill switch 503, spending 429, per-IP and per-user rate-limit 429 with `Retry-After`) and validate against `ErrorEnvelope` / `RunFailedEnvelope` / `DetailEnvelope`; table test asserts status+code pairs equal today's behaviour and every emitted code is in the documented set.
4. **Unexpected shape handling:** negative tests feed mutated bodies (extra key, missing key, string where int expected, float money) and assert the models **reject** them, proving the drift alarm works; a canary test deliberately adds a field in a patched producer and confirms the conformance test fails.
5. OpenAPI: existing snapshot-equals-render test; new test that every covered route lists its response schema and error responses, that `response_model is None` for covered routes, and that `ToolResults` has all 18 keys equal to `agents.tools.SPECS`.
**Proof that behaviour is unchanged.** (a) *Golden diff*: before editing, on the current commit, run the synthetic scenario with a frozen clock and record canonical JSON (sorted keys) of every covered route and tool response plus status codes and relevant headers into `tests/contracts/golden/`; after B3, rerun and require byte equality (any serialisation change, including `Z` vs `+00:00`, fails). (b) The **entire existing backend suite** passes unmodified: record the baseline counts at step 0 (the last recorded full run was 611 passed, 1 skipped; a stale earlier run showed a migrations-test failure that must be re-verified, not assumed), then require the same pass count plus the new tests, with ruff, mypy and format clean. (c) A reviewer checklist and a `git diff` gate: changes to `services/api/finance.py`, `services/api/coach.py` and `services/api/orchestrator.py` are limited to imports and `responses=` decorator arguments (no body, signature or return change); a test fails if any covered handler's signature or return annotation changed. (d) No file under `database/`, `core/permissions/`, `services/api/auth/` or `domain/*/service.py` may change.
**Acceptance criteria.** All four routes and 18 tool results have models with golden and live conformance tests green; error envelopes and every status/code pair documented and asserted; zero diff in response bytes (golden); existing suite and static checks green; snapshot regenerated and `api:types:check` green in GitHub Actions; mobile `schema.d.ts` diff reviewed with no regression to existing types; no new dependency; no migration; no workflow change; synthetic-only fixtures with scan passing; report with commit SHA, test counts and the OpenAPI diff summary.

## 10. Security and privacy review
- **No new exposure.** Models describe what routes already return; no field is added, no route widened. `extra="forbid"` plus conformance tests mean a future accidental leak of a new field (for example message text) fails tests instead of shipping silently.
- **Sensitive content.** Finance labels and coach titles are decrypted user text and message-derived `topics` exist today; models carry no examples from real data, schema `description`/`examples` use invented values only, and fixtures are scanned. Memory text is never in any response (counts only), unchanged.
- **Privacy rule preserved.** `last_message_intent`, `flagged_messages` and `topics` stay agent-visible only for shared conversations (B1 rule); a conformance test re-asserts the unshared case returns `{"error":"not_shared"}` and the inbox shows no content-derived field.
- **Runtime safety.** Documentation-only wiring cannot filter or alter responses; the `response_model is None` guard prevents later accidental enforcement. No auth/authorization code is touched; rate limiting, kill-switch and governance paths are only exercised by tests.
- **Schema exposure.** The OpenAPI document is still off by default, authenticated in dev only, never served in production, and exported offline; B3 enlarges it but does not change who can read it.
- Logs/fixtures/goldens contain no tokens, secrets or real identifiers; the test harness already uses throwaway databases and mock model.

## 11. Risks, unresolved questions and implementation sequence
**Risks.** (1) Hidden shape variants not covered by the scenario (mitigated by exhaustive nullable-branch tests and `forbid`). (2) Golden byte-equality is brittle to unrelated serialisation changes (accepted: that is the point). (3) Large OpenAPI growth and noisy generated types (reviewed once). (4) F1 will be visible the moment a plan with blocks is tested; it must not be "fixed" inside B3. (5) A mismatch between `forbid` strictness and legitimate additive backend evolution; the alarm is intended, but contributors must update contracts deliberately. (6) Test environment: integration tests need Docker/Postgres; baseline health must be re-established first.
**Decisions requested.** **D1** documentation-only `responses=` (recommended) versus enforced `response_model`. **D2** surface `ToolResults` via OpenAPI post-processing (recommended, no core edit) versus `json_schema_extra` on `OrchestratorResponse.data`. **D3** insight `params` typing (a, recommended) versus per-code union (b). **D4** approve a separate backend `openapi check` CI job. **D5** open `str` for `code`/status fields (recommended) versus closed enums. **D6** F1 coach-plan summary defect: approve a separate bug-fix task (recommended after B3).
**Sequence.**
0. Baseline: bring up the test stack, run the full backend suite and record counts; build the synthetic scenario with a frozen clock; capture golden bodies/status codes/headers; enumerate all emitted error codes; confirm F5, F11 and F1 empirically (read-only).
1. `contracts/common.py`, `errors.py` and unit tests with hand-written synthetic fixtures.
2. Finance models (R1-R3, T1-T9) + unit tests.
3. Coach models (R4, T13-T18) + unit tests.
4. Messaging and `ToolResults` models (T10-T12, wrapper) + unit tests.
5. Wire `responses=` on the four routes and the orchestrator post-processing; add guard tests (`response_model is None`, signatures unchanged).
6. Live conformance tests (success branches, nullable branches, errors).
7. Golden re-run (byte equality) and full backend suite plus ruff/mypy.
8. Export snapshot; mobile `npm run api:types`, `check:all`; review generated-type diff; GitHub Actions run.
9. Completion report (SHA, counts, OpenAPI diff summary, F1-F12 status). Stop; wait for approval before M8.2 implementation.
