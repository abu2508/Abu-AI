# M8.2 Home Dashboard and Orchestrator Integration: implementation plan (for approval; nothing implemented)

Status: PLAN ONLY. Prepared 2026-11-24 after M8.1 approval. Synthetic data and the mock model only. The four production gates stay **BLOCKED**. No backend change is proposed inside M8.2; where the backend is insufficient, it is listed as a separate, optional task (section 9) that needs its own approval.

Evidence base: the committed OpenAPI snapshot (`mobile/openapi/openapi.json`, 108 operations) and the backend source it was exported from (`services/api/orchestrator.py`, `core/orchestrator/*`, `agents/workflows.py`, `agents/summaries.py`, `services/api/{finance,coach,messaging,governance}.py`, `domain/*/service.py`). Nothing below is invented: each field is marked **schema** (declared in OpenAPI) or **source** (read from backend code, not in OpenAPI, so it must be pinned by a recorded contract fixture before use).

## 1. Scope
In: a live Home dashboard (when connected to an approved development backend), the Ask Abu result-card experience over `POST /v1/orchestrator/run`, recent-asks metadata, loading/offline/error/401/429/kill-switch handling, user-scoped caching, tests.
Out: Finance, Messages and Coach tab live data (M8.3 to M8.5), memory approval UI, any write to finance/messaging/coach, drafting-to-send, push, Face ID lock, voice, widgets, production endpoints, real data, any external model.
Demo mode stays the default and unchanged in behaviour: not connected means the current synthetic fixtures with "Synthetic data" and demo labels, and zero network calls.

### 3.2 Ask Abu
`POST /v1/orchestrator/run` (**schema**): body `{message: 1..4000 chars, conversation_id?: uuid}`, `extra="forbid"` (no user/agent/model/workflow field exists), optional `Idempotency-Key` (16..128 chars, `[A-Za-z0-9_-]`). Response `OrchestratorResponse`:
`run_id`, `status` (`completed | clarification_needed | unsupported | failed`), `intent`, `confidence`, `agent_id`, `workflow`, `mock` (always true now), `reply` (mock-model text), `clarification_question`, `summary` (deterministic template built from `data`, "no model wording, no invented figures"), `data` (**untyped**, `{ "<tool name>": result }`), `context {items, rules, basis, note}` (counts only), `memory_proposals[] {id,status,needs_confirmation}`, `usage {steps,input_tokens,output_tokens,cost_inr,attempts}`, `warnings[]`, `error`, `replayed`, `reply_expired`, `execution_id`, `trace_id`.
History (**schema**): `GET /v1/orchestrator/runs?limit&before` returns `RunSummary[]` (metadata only: status, outcome, intent, workflow, error_code, created_at, `response_available`); `GET /v1/orchestrator/runs/{id}` returns `RunDetail` (`response` only while stored; `reply_expired` after the retention window). The request text is never returned by the server.
`GET /v1/orchestrator/workflows` (**schema**): 17 workflows (finance: assistant, budgets, subscriptions, loans, cards, statements, transactions; messaging: reply_assist, conversation_summary; coaching: daily_plan, briefing, review, goals, habits; general) with `description` and `tool_allowlist`; used to label cards and to build suggestion chips, never to choose a workflow (routing is server-side).

### 3.3 Tool-result shapes inside `data` (all **source**, from `agents/summaries.py` and `agents/tools.py`)
`finance.summary` (income, expense, net, pending_review_count) | `finance.insights` (`insights[].text/severity`) | `finance.budget_status` (`budgets[]`: category, spent, limit, status) | `finance.upcoming` (`upcoming[]`: kind, label, amount, due) | `finance.loans` (`loans[]`: label, outstanding_principal, emi, next_due) | `finance.cards` (`cards[]`: label, owed, utilisation_pct, band) | `finance.subscriptions` (`active[]`, `suggested[]`) | `finance.cashflow` (closing, projected_month_expense) | `finance.pending_count` (pending_review) | `messaging.analyse` (message_count, needs_reply, last_message_intent) | `messaging.reply_suggestions` (`drafts[].text`) | `messaging.summary` (summary) | `coach.plan` (blocks, unscheduled) | `coach.briefing` | `coach.review` (tasks_completed_today, habits_done, habits_due, carry_over) | `coach.progress` (window_days, tasks_completed, tasks_open) | `coach.habits` (`habits[]`: title, current_streak) | `coach.goals` (`goals[]`: title, progress_pct, progress_state). ## 5. Ask Abu: structured result cards (not a chat transcript)
Principles: one question, one result; no message bubbles, avatars or scrolling transcript; the server does not return request text, so the app never rebuilds a conversation. The submitted question is held only in memory for the visible result and is discarded on dismiss, new question, logout, expiry or app background.
Layout: orb + prompt field + suggestion chips; below, a **Result stack** (single current result) and a **Recent asks** list (metadata from `GET /runs`).
Result card anatomy (always in this order): header (workflow label from `workflows`, intent, "Mock model" chip, "Synthetic data" chip) -> **Answer** (`summary`, authoritative, deterministic) -> **Detail sections** from `data` -> **Draft/Reply** (`reply`, labelled "Mock model wording", secondary) -> **Footnotes** (context counts "used N saved facts", warnings, usage steps/cost INR, "Replayed" badge, ids behind a "Details" disclosure).
Card variants by `status`:
- `completed`: sections by tool key: MoneySummary, Insights, Budgets, Upcoming, Loans, Cards, Subscriptions, Cashflow, ConversationAnalysis, ReplyDrafts (each draft labelled "Draft. Abu never sends messages"; no send button), DayPlan, Briefing, Review, Progress, Habits, Goals. Money rendered with the BigInt formatter from strings; never parsed as float.
- `clarification_needed`: ClarificationCard with `clarification_question` and quick-answer chips (the user types a new question; no hidden thread state).
- `unsupported`: NoticeCard explaining Abu will not do this (payments, transfers, sending), using the server's static text.
- `failed`: ErrorCard mapped from `error.code` (see 6).
- `memory_proposals`: a compact "Abu suggested N things to remember. Review them in Memory (coming later)" line; **no approval controls in M8.2** (approval stays a later, explicit milestone item; never silent).
Optional `conversation_id`: a "About a conversation" picker populated from `GET /v1/messaging/inbox` limited to shared conversations; defer if you prefer (decision D3).
Idempotency: each submission gets one random `Idempotency-Key` held in memory for the card's lifetime. After a timeout or lost response the same key is replayed (`replayed: true` shown), so a retry cannot create a second run; 409 `request_in_progress` shows "Still working, check Recent asks" and polls `GET /runs/{id}` (bounded). The key and question are **not persisted**; killing the app mid-request means the user asks again (documented; a persisted retry record would store the question text on disk, which we refuse).

## 6. Loading, offline and error handling
Per-card state machine: `idle -> loading -> ready | empty | error(code)` with skeletons (no layout shift), Reduce Motion respected, live-region announcements.
| Condition | Source | UX |
|---|---|---|
| Not connected | status `unenrolled` | Demo fixtures + demo banner; no calls. |
| Offline | `expo-network` / `offline` code | "Offline" chip; Home shows last in-memory data marked "as of hh:mm" for this session only (no disk cache); Ask Abu disabled with explanation; **never queued**, nothing sent on reconnect. |
| 401 | `unauthorized` | M8.1 flow (refresh once, replay once); if the session ended, status `expired`, caches cleared, Home returns to demo with a "Session ended, reconnect" banner. |
| 403 | `governance_refused`, `permission_denied` | ErrorCard "Abu isn't allowed to do that". |
| 409 | `idempotency_conflict`, `request_in_progress` | see 5. |
| 422 | `invalid_request` | inline field error (1..4000 chars). |
| 429 (rate limit) | body `{"detail":"rate limit exceeded"}` + `Retry-After` | countdown, auto re-enable; Home pull-to-refresh disabled until then. |
| 429 (`spending_blocked`, `limit_exceeded`) | `error.code` | "Spending limit reached" / "per-run limit reached", no automatic retry, no countdown. |
| 503 `kill_switch_active` | `error.code` | Status banner "Paused by the safety switch"; Ask Abu disabled; **Home own-data cards keep loading** (domain read routes stay available during the kill switch by design). |
| 503 other (`model_unavailable`, `memory_unavailable`, `governance_unavailable`, "service unavailable") | code/detail | "Temporarily unavailable"; manual retry. |
| 504 `timeout`, 500 `internal_error`, network, contract | | retry affordance; contract errors never render partial data; fixed messages only. |
The status banner reads `GET /v1/governance/status` on Home focus and after any 503; it is the single source for the paused state.

## 7. Screen specifications
**Home (connected).** Header with Synthetic and Dev-backend chips (+ Offline chip). 1) Status card (orb, "All systems normal" or "Paused"). 2) Today card: next 2 plan blocks, event count, open habits, "Goal needs attention", due reminders. 3) Money card: net, income, spending, savings rate, "N items await your review and are not counted", optional top insight and next due. 4) Needs a reply: up to 5 inbox rows (privacy rule: intent text only when `shared_with_assistant`). 5) "Ask Abu" button. Each card: own skeleton/error/empty state, tap targets >= 44 pt, labelled, Dynamic Type safe, Light/Dark. Pull-to-refresh re-reads all four.
**Ask Abu.** States: idle, composing, thinking (orb), result (variants above), error (variants above), disabled (offline/paused/not connected, in which case the existing local demo remains with its "Demo only" label). Suggestion chips come from a fixed list plus workflow descriptions. Close returns to the previous tab.
**Recent asks** (sheet under Ask Abu): `GET /runs?limit=20` rows (workflow label, status, time, "response available/expired"); tapping opens `GET /runs/{id}` rendered with the same card components; no request text because none exists.
**Demo parity.** The current HomeScreen/AssistantScreen render exactly as in M8.1 whenever status is not `authenticated`; live and fixture data are never mixed inside one card.

## 9. Security and privacy
- All data user-scoped: every query key `['u', userId, ...]`; cache cleared on logout/expiry/enrolment (M8.1 machinery); the result card, question text and recent-asks list live in component/query state that is cleared with it; nothing is persisted to disk (no AsyncStorage, no persister).
- The question text is never logged, never in query keys or URLs, never in analytics, never copied to the clipboard by the app; the redacting logger records only route templates and status.
- Server text is never rendered as markup; `reply` and drafts are plain text; any unknown field is ignored; `error.message` is discarded (fixed client messages).
- Memory text is never in a response (counts only); the UI never asks for it.
- No send/pay/transfer controls exist anywhere; drafts are labelled "Abu never sends".
- Money is string-only end to end (BigInt formatting).
- Idempotency key: CSPRNG, memory only.
- Demo mode unchanged: zero network; synthetic chips on every screen; live mode adds the Dev-backend chip.
- **Carried forward (explicit):** (a) **React Native redirect risk.** RN's fetch may follow a redirect before the client's origin check, so an `Authorization` header could reach a redirect target. M8.2 adds a **spike (step 1)**: against a local test server that 302s to a second origin, prove on the device and in Jest-with-real-HTTP whether the header leaks with the current transport and whether `expo/fetch` with `redirect:"manual"` prevents it; adopt the safer transport if it does, otherwise keep the risk documented and rely on operator-owned never-redirecting backends. (b) **Physical-device verification** remains required before any native claim: Keychain behaviour, expo-network, background/foreground, app kill mid-request, offline/online transitions, Dynamic Type, Reduce Motion, VoiceOver. Plan: a written device checklist run on your iPhone with Expo Go (no Apple Developer Program needed for this) against the private Codespaces URL; until you run it, every M8.2 native statement is marked **unverified**.
- Four production gates remain BLOCKED and shown in About; no external model provider; no real personal data.

## 10. Tests and acceptance criteria
**Unit/component (Jest, injected fake transport):** zod schemas against recorded fixtures (valid, missing field, wrong type, extra field, float-like money); card mapper table test for every tool key plus unknown key plus `{"error":...}` plus truncated data; error mapper for every code and both 429 kinds (Retry-After parsing); run flow with same-key replay after timeout, 409 in progress, 401 mid-flow, offline fast-fail with zero requests and nothing sent on reconnect; kill switch with Home own-data cards still loading; per-card independent failure; user A -> logout -> user B shows no cached card, question or recent run; question text absent from logs, query keys and storage (static + runtime scans); demo mode makes zero network calls and indicators persist; accessibility (44 pt, labels, Dynamic Type, Reduce Motion, live regions) for Home, Ask Abu, Recent asks; Light and Dark rendering tests.
**Contract (local Docker backend, synthetic data, mock model; reported separately from CI):** record real bodies for each Home read and for every reachable workflow's `data`; run a real orchestrator request per workflow family; real 401 after revocation, real 429 rate limit with `Retry-After`, real kill-switch 503 (`kill_switch_active`) with domain reads still 200, real idempotent replay (`replayed: true`) and 409 conflict. To be verified in the first spike: the in-process mock model answers without LiteLLM reachable (otherwise start the dev LiteLLM overlay).
**Quality gates:** `check:all` green on GitHub Actions from a clean checkout; coverage >= 90% lines and branches for the new data/card modules; secret and real-data scan extended to the new fixtures.
**Acceptance:** Home shows live synthetic data per card with correct loading/empty/error states; Ask Abu produces structured cards for all four statuses without any chat transcript; every listed error path has a test and a screenshot; demo parity unchanged; no backend file changed; screenshots Light/Dark for Home (loading, ready, offline, paused, partial failure), Ask Abu (idle, thinking, each result family, clarification, unsupported, failed, 429, paused), Recent asks; device checklist delivered and clearly marked unverified until you run it; completion report with commit SHA, CI run, contract results, coverage, security checklist, limitations.

## 12. Risks and unresolved gaps
1. Untyped finance/coach/tool-result contracts (G1/G2): mitigated by recorded fixtures and contract tests, fully resolved only by backend task B3 (needs your approval).
2. Redirect/Authorization leakage on React Native: unresolved until the spike and device verification.

4. The model is the mock: card layouts are validated against deterministic `data`/`summary`, not real model prose; real-model behaviour is out of scope and gated.

6. Rate limits: Home fan-out is 4 to 6 reads per refresh; no polling; countdown UX for 429.
7. `summary` text is server-authored English and not localised.
8. The 20 moderate dev-tooling advisories, native install-script verification, bundle ID and native icon checks remain open carry-forwards.
