# M8.1 Authentication and Secure API Foundation: implementation plan (for approval; nothing implemented)

Status: PLAN ONLY. M8.1 implementation starts only after explicit approval. Synthetic data and the mock model only. The four production
security gates stay **BLOCKED**. No backend security control is weakened. No credentials, provider keys or GitHub tokens ship in the app.

## 1. Scope and non-goals
In scope: device enrollment, secure token storage, in-memory access token, single-flight refresh, idempotent refresh retry, an
authenticated API client, session management, logout/revocation, offline and error handling, tests, CI.
Out of scope: finance/messaging/coach feature screens (M8.3+), push notifications, biometrics-gated actions beyond an optional app lock,
extension credentials (G8 stays deferred: extensions never hold or rotate credentials), any production endpoint, any real data,
payments, message sending, QR enrollment (optional, see decision D3).

## 2. Backend contract (existing, unchanged)
| Route | Auth | Notes |
|---|---|---|
| `POST /v1/auth/enroll` `{enrollment_code(8-128), device_name(1-128), platform}` | public | returns `{access_token, token_type, expires_in, refresh_token, session_id}`; single-use code, hashed server-side, rate limited 10/min/IP |
| `POST /v1/auth/refresh` `{refresh_token}` + header `Idempotency-Key` (16-128, `[A-Za-z0-9_-]`) | public | rotates the refresh token; same key on retry returns the same pair; reuse of a rotated token without the key kills the whole session |
| `POST /v1/auth/logout` | Bearer | 204, revokes the current session |
| `GET /v1/auth/sessions` | Bearer | list with `current` flag |
| `DELETE /v1/auth/sessions/{id}` | Bearer | 204 / 404 |
| `GET /v1/me` | Bearer | `{user_id, session_id}`; used as the "am I signed in" probe |

Lifetimes: access 10 min, refresh 30 days, session max 90 days. Rate limits 10/min auth per IP, 300/min per user. Kill switch returns 503
for model-backed routes while own-data routes stay available. Money is a string.

## 3. Architecture
```
mobile/src/auth/
  secureStore.ts        thin wrapper over expo-secure-store (refresh token + session id + device id only)
  tokenVault.ts         in-memory access token + expiry (module-private, never persisted, never logged)
  refreshCoordinator.ts single-flight refresh, persisted Idempotency-Key, retry policy
  authClient.ts         enroll / refresh / logout / sessions (the only unauthenticated calls)
  sessionStore.ts       zustand store: status = unenrolled | restoring | authenticated | expired | locked | offline
  useAuth.ts            hooks for screens
mobile/src/api/
  client.ts             fetch wrapper: base URL from allowlist, Bearer injection, zod validation, ApiError mapping
  errors.ts             ApiError union (Unauthorized, Forbidden, NotFound, RateLimited, KillSwitch(503), Offline, Timeout, Server, Contract)
  schemas/              zod schemas for the M8.1 routes only (auth, me, sessions)
mobile/app/(auth)/enroll.tsx      enrollment screen (code entry, device name)
mobile/app/settings/sessions.tsx  session list and revoke
mobile/app/settings/index.tsx     adds "Sign out" and connection status
```
Demo mode stays the default and still performs no network calls. Enrollment is only reachable when a backend URL passes the existing
allowlist (private Codespaces URL or debug localhost); production builds refuse any URL.

### 3.1 Enrollment
1. User opens Settings -> Connect to backend (dev builds only; hidden in demo mode).
2. User pastes an enrollment code generated by the backend operator (CLI) and optionally edits the device name (default from `expo-device`).
3. `authClient.enroll` sends the code over HTTPS to the allowlisted URL. The code is held in component state only, cleared on success/failure,
   excluded from logs and error reports, and never stored.
4. On success: refresh token -> Keychain; access token -> memory; session id and device id -> Keychain; store flips to `authenticated`.
5. Failure mapping: unknown/expired/used code -> a single generic "code not accepted" message (no oracle); 429 -> wait message with `Retry-After`; network -> offline message.

### 3.2 Secure storage (Keychain)
- `expo-secure-store` with `keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY` (no iCloud Keychain sync, no backup migration; a restored
  device must re-enroll).
- Stored: refresh token, session id, in-flight refresh `Idempotency-Key` + the token it belongs to. Nothing else. No access token, no
  enrollment code, no user data.
- Optional app lock via `expo-local-authentication` (decision D2): `requireAuthentication` is *not* used for the refresh token (it would
  block background refresh); instead the UI gate locks the screen and the in-memory access token is dropped on lock.
- Wrapper handles `SecureStore` unavailability (e.g. web, Jest) with an explicit in-memory test double; production code never falls back to
  AsyncStorage or any plaintext store.

### 3.3 In-memory access token and shared refresh coordination
- The access token lives only in `tokenVault` (module scope, not in React state or devtools, not serialised). It is dropped on logout,
  lock, app termination and `expired`.
- `getAccessToken()` returns the cached token when it has more than 60 s left (jittered), otherwise awaits `refreshCoordinator.refresh()`.
- **Single-flight:** concurrent callers share one in-flight promise. A 401 from an authenticated call triggers at most one refresh and one
  replay of the original request; a second 401 ends in `expired`.
- **Cross-process safety:** one JS runtime per app today; the coordinator keys its lock on the refresh token it read, so a stale rotation
  (e.g. after a crash mid-refresh) is recovered via the idempotent retry below, not by guessing.

### 3.4 Idempotent retry
- Before sending a refresh, generate a 128-bit random `Idempotency-Key` and persist `{key, refreshTokenFingerprint}` to Keychain.
- On success, atomically write the new refresh token, then clear the key. On a lost response, timeout or crash, the next refresh reuses the
  same key with the same old token, so the backend returns the already-issued pair instead of treating it as token reuse.
- Retry only network errors/timeouts/5xx (not 401/403/429-with-long-Retry-After): exponential backoff with jitter, max 3 attempts, total
  budget 20 s. 401 on refresh = session dead -> wipe Keychain -> `unenrolled` with a clear message. 429 honours `Retry-After`.
- Write ordering is specified and tested: new token is persisted before the key is cleared; if persisting fails the store goes to `expired`
  rather than continuing with an unrecoverable token.

### 3.5 Authenticated API client
- Base URL only from the allowlist (`backendAllowlist.ts`); HTTPS required except debug localhost; no redirects to other origins
  (`redirect: "error"` equivalent check); request timeout 15 s via `AbortController`; `Authorization` set only by the client, never by callers.
- Every response is parsed with a zod schema; a mismatch becomes `ContractError` (never rendered as data) and is reported in dev builds.
- Money stays a string; no `parseFloat`; existing BigInt formatter is used.
- Headers: `Accept: application/json`, `X-Client: abu-mobile/<version>`; no user identifiers in headers or URLs.
- Logging: structured, redacting (`Authorization`, `refresh_token`, `enrollment_code`, `Idempotency-Key`); a unit test scans log output.
- TanStack Query configured with `retry: false` for auth and mutations, conservative retry for GETs, no persistence of cache to disk in M8.1.

### 3.6 Session management, logout, revocation
- Sessions screen: list devices (name, platform, created, last used, expires), "This device" badge, revoke other sessions
  (`DELETE /auth/sessions/{id}`), confirmation dialog, optimistic update with rollback.
- Logout: best-effort `POST /auth/logout`; regardless of the network result, wipe Keychain and memory and clear TanStack Query cache.
  If the server call fails the UI says the server session may still be active and offers "Revoke from another device".
- Remote revocation or session expiry: next call returns 401 -> refresh fails -> `expired`, local wipe, return to enrollment.
- 90-day session maximum: show "session expires on <date>" from `GET /auth/sessions`.

### 3.7 Offline handling
- Connectivity via `expo-network` (or fetch failure classification; decision D4). Offline never wipes credentials.
- `offline` is a status overlay, not a sign-out: reads show the last in-memory result or an offline empty state; mutations are not queued in
  M8.1 (explicitly deferred) and fail fast with `OfflineError`.
- Refresh is attempted only when online; on reconnect, the first request refreshes if needed. Idempotent retry covers a drop mid-refresh.
- 503 kill switch is shown as "Abu AI is paused by the safety switch"; own-data routes keep working.

## 5. Tests
Unit/component (Jest, msw for HTTP):
- Token vault: never persisted, cleared on logout/lock; not reachable from store state or logs.
- Secure store wrapper: exact options (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`), only the allowed keys written, no plaintext fallback.
- Single-flight: 50 concurrent requests with an expired token cause exactly one refresh call.
- 401 handling: one refresh + one replay; second 401 -> `expired`; replay is not looped.
- Idempotent retry: lost response then retry sends the same key and token, yields the same pair; new token persisted before key cleared;
  crash-simulation between steps recovers; persistence failure -> `expired`.
- Backoff/jitter bounds, `Retry-After` handling, no retry on 4xx.
- Enrollment: success, wrong/expired/used code (generic message), 429, offline, code never stored/logged, field validation.
- Logout: wipes Keychain, memory and query cache even when the network call fails.
- Sessions: list, current badge, revoke other, 404 handling, cannot revoke current via the "other" path without logout semantics.
- API client: allowlist enforcement, no cross-origin redirect, timeout, zod mismatch -> ContractError, error mapping table,
  Authorization injected only by the client, log redaction scan.
- Offline: status overlay does not wipe credentials; mutations fail fast; reconnect refreshes.
- Demo mode: still makes zero network calls; Settings shows the connect option only for allowlisted dev URLs.
- Accessibility: new screens meet 44 pt targets, labels, Dynamic Type, Light/Dark contrast, Reduce Motion.
- Secret scan extended: no tokens, enrollment-code-shaped strings or URLs outside the allowlist in source/bundle.

Contract tests (opt-in script `npm run test:contract`, not in default CI): run against the live Docker backend started locally with
synthetic data (enroll with a freshly generated code, refresh with and without Idempotency-Key, forced token-reuse behaviour, logout,
sessions list/revoke, rate limit 429 behaviour). Results reported as local, clearly separate from CI. A later change can add a CI job with
a service container; not part of M8.1 unless you approve it (D5).

CI: existing `mobile.yml` gains no new secrets; the same gates run (`check:all`). Coverage threshold for `src/auth` and `src/api`
(>= 90% lines/branches) enforced in Jest config.

## 7. Backend dependencies and risks
- Enrollment codes are created by the operator (backend CLI); the app only consumes them. Documenting the operator steps is a docs-only
  deliverable (no backend change).
- Auth routes have response models (typed in the OpenAPI snapshot); `/me` returns an untyped dict, so the client validates it with zod
  and the carry-forward "backend response typing" item stays open.
- Option B connectivity (private Codespaces URL) means cookies, ATS and certificate behaviour differ from a real device on a cellular
  network; reported as unverified until device testing (carry-forward 1).
- Keychain behaviour cannot be exercised on Linux CI; unit tests use a double, so real Keychain accessibility remains a device-verification
  item.
- Clock skew: expiry is computed from `expires_in`, not from the device clock against a JWT claim.
